# ADR-0003: Ссылки в обзоре собирает код по ID

- **Статус:** accepted
- **Дата:** 2026-10-20
- **Связано:** design-doc §5.1 (принцип 4), §3, §5.6

## Контекст

LLM-ассистенты выдумывают ссылки: по данным OpenScholar, GPT-4o — в 78–90% случаев на научных вопросах. Выдуманная ссылка — самая дорогая ошибка: пользователь доверяет цитате. Кроме того, ссылки, сгенерированные текстом, нельзя надёжно проверить автоматически.

## Решение

- **Writer не пишет библиографию и не форматирует ссылки.** Он вставляет только идентификаторы пропозиций или claims из ledger (`[P12]`).
- **Рендерер** (`research_helper.render`):
  - разрешает ID в ссылку с автором, годом и URL;
  - показывает цитату из span при наведении;
  - **отклоняет неизвестные ID** — это ошибка валидации, а не предупреждение.
- **Список литературы** генерируется кодом из метаданных `Paper`.

## Альтернативы

| Вариант | Плюсы | Минусы | Почему нет |
|---|---|---|---|
| LLM пишет ссылки, потом проверка существования | Привычно | Выдумки возможны, проверка ловит не всё | Убираем класс ошибок целиком, а не ловим его |
| Ссылки только на уровне статьи | Проще | Нельзя проверить, какой фрагмент что подтверждает | Нужна проверка на уровне утверждений (G1) |

## Последствия

- **Плюсы:** выдуманная ссылка невозможна по построению. Остаётся только неверная атрибуция, и её измеряет аудитор и независимый судья.
- **Минусы:**
  - Writer ограничен ledger и не может сослаться на то, чего там нет;
  - промпты Writer должны надёжно соблюдать формат ID — нужна валидация и одна попытка исправления.
- **Что дальше:** в схеме ID пропозиций и claims стабильны в пределах прогона (`src/research_helper/schemas/ledger.py`).

## Когда пересмотреть

Если оценка покажет, что ограничение «только из ledger» заметно снижает полноту обзоров по сравнению с B3 при равной достоверности.
