# Неделя 1: разведка и проверка запаса для улучшения

*Домашний домен: ML/NLP · перенос: биомед · см. [design-doc.md](../design-doc.md) §10*

**Цель недели** — ответить на вопрос «есть ли что улучшать?» до того, как писать собственную систему. Для этого нужно:
- посмотреть, как ошибаются голая LLM, ванильный STORM и PaperQA2 на ML/NLP-вопросах;
- начать собирать два ключевых ручных актива: golden set и разметку для калибровки судьи.

Собственный код на этой неделе — только обвязка: запуск чужих систем, проверка ссылок и подсчёт разметки.

Без ключа S2 работает через общий пул: 21.10 первый же запрос получил 429. Пока ключа нет, поиск идёт через OpenAlex и arXiv — оба отвечают без заявки.

## День 2 — FreshSci-dev v0 (6–8 ч)

10 вопросов по ~45 минут. **Пишутся до запуска любых систем**, иначе ключевые пункты подстроятся под их ответы.

**Смесь типов вопросов:**

| Тип | Сколько | Пример формулировки (ответ не предрешён) |
|---|---|---|
| effectiveness | 3 | «Улучшает ли chain-of-thought качество на задачах без многошагового рассуждения?» |
| comparison | 2 | «Process reward model vs outcome reward model для reasoning в математике: что известно?» |
| methods_survey | 2 | «Какие методы снижают self-preference bias у LLM-as-a-judge?» |
| controversy | 2 | «Long context vs RAG: когда что выигрывает?» |
| mechanism | 1 | «Почему DPO может снижать разнообразие генераций?» |

**Правила:**
- В каждом вопросе — 5–10 ключевых пунктов, 3–8 ключевых статей (arXiv ID), известные противоречия, ожидаемый вердикт.
- Хотя бы 5 из 10 вопросов **свежие**: половина ключевых статей вышла после cutoff выбранной LLM.
- В 2–3 вопросах должно быть известное противоречие: по ним проверяется, находят ли системы конфликты.
- Пометить 5 вопросов для прогонов дней 3–4. Брать разные типы, обязательно с одним controversy.

## День 3 — B0 и ванильный STORM (3–4 ч)

**B0 (без retrieval):**
- Попросить ответ со списком литературы (название, год, venue).
- Скриптом проверить, существует ли каждая ссылка: поиск по названию в S2 или OpenAlex с нечётким совпадением. Это задача [T-0003](../tasks/0003-b0-citation-checker.md).
- Результат — **доля выдуманных ссылок**. Это первая цифра для отчёта и мотивация всего проекта.

**STORM** (`pip install knowledge-storm`):
- **Retriever.** Из коробки есть веб-поисковики. Bing Search API Microsoft закрыл в 2025 г., так что `BingSearch` не подойдёт. Рекомендация — **написать свой RM поверх Semantic Scholar snippet search** по образцу классов в `knowledge_storm/rm.py`. Это ~50 строк, и тот же адаптер потом станет источником для нашей системы, то есть baseline B3 будет искать там же, где и B4 (ADR-0004, задача [T-0002](../tasks/0002-s2-retriever-for-storm.md)). Запасной вариант, пока нет ключа S2, — Tavily или Serper с ограничением на `arxiv.org`, с пометкой в ADR.
- Сохранять статью, логи диалогов, outline, список URL, время, токены, стоимость.

## День 4 — PaperQA2 (3–4 ч)

- `pip install paper-qa`. PaperQA2 работает по **локальной папке с PDF**: на каждый вопрос скачать 15–30 OA-статей с arXiv.
- Как собирать папку: ключевые статьи из golden set + top результатов поиска S2 по вопросу. Это частично «оракульная» библиотека, отметь это в отчёте, она завышает результат PaperQA2.
- Тот же вопрос, та же LLM. Сохранять ответ, контексты, стоимость.

## День 5 — разметка и разбор ошибок (5–6 ч)

- Из каждого из 15 ответов случайно взять 10 утверждений (стратифицированно по разделам) → 150 пар. Разметить по [гайду](../labeling-guide.md), ~2 минуты на пару.
- **Повторная разметка:** 20 пар разметить ещё раз через 3–4 дня, не глядя на первые метки. Это даёт оценку собственной согласованности. Если есть коллега — лучше он.
- Отдельно по golden set для каждого ответа:
  - какие ключевые пункты покрыты;
  - найдено ли известное противоречие;
  - есть ли ссылки на ключевые статьи.
- Эти 150 пар — **начало калибровочного набора судьи**: на неделе 2 добрать до 200–300.

## Выходные / буфер — отчёт и Gate 0

`reports/week1-failures.md`:
1. Таблица: система × {SUPPORTED, PARTIAL, NOT_SUPPORTED, CITATION_INVALID} + теги ошибок + покрытие пунктов + найденные конфликты + стоимость и время.
2. 3–5 характерных примеров ошибок с цитатами.
3. Решение Gate 0.

### Gate 0: есть ли запас для улучшения

На 5 вопросах это **сигнал, а не результат**: доверительные интервалы будут широкими. Пороги ниже — ориентиры, а не правила.

| Что увидели | Решение |
|---|---|
| У STORM заметная доля NOT_SUPPORTED + PARTIAL (ориентир ≥10–15%) **и/или** часто пропускаются пункты или конфликты | H1/H2 в силе, идём по плану |
| Ссылки у STORM почти всегда подтверждаются, но пропускаются конфликты и ключевые пункты | Фокус на полноту (H2), поиск противоречий и рубрику доказательности (H5); verifier остаётся, но не главный тезис |
| Все системы хороши по всем осям | Вопросы слишком лёгкие: сделать их сложнее (controversy, свежие, узкие), прежде чем менять проект |
| PaperQA2 заметно лучше STORM по достоверности | Сильный baseline: B4 должен обгонять PaperQA2, а не только STORM; учесть в позиционировании |

## Риски недели

| Риск | Что делать |
|---|---|
| Ключ S2 задерживается | OpenAlex + arXiv API без ключа; для STORM — Tavily/Serper по arXiv, с пометкой в ADR |
| Golden set занимает больше времени | Оставить 10 вопросов, но сократить пункты до 5; не жертвовать правилом «до прогонов» |
| Расходы выходят из-под контроля | Лимит у провайдера; STORM с меньшими `max_conv_turn` и `max_perspective` |
| Разметка утомляет и плывёт | Сессии по 45 минут; повторная разметка 20 пар покажет дрейф |
